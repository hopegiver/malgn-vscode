## 요약 (2분 규칙)

라운드1은 "화면이 실패를 0으로 바꿔 말한다"를 잡았고, 그 수정은 실제로 먹혔다
(`r1__home__error.png` → `r1-final__home__error.png` 대조에서 위젯 5개가 전부 정직해졌다).
**이번 라운드의 관통 문제는 "그 수정을 한 칸씩 덜 발랐다"** 는 것이다 — 홈 위젯 7개 중
6개는 고쳤는데 사용량 위젯 하나가 아직 실패를 "기록이 없습니다"로 말하고(U-23),
목업 토글은 마켓플레이스에서만 지우고 카탈로그에 남은 쪽은 그대로다(V-01).
둘 다 같은 커밋에서 같은 논리로 처리했어야 할 자리이고, 둘 다 수정 비용이 5줄 이하다.

**새로 판 프론티어에서는 세 종류가 나왔다.** ①조작 이후 화면에서 플레이스홀더가 새어나온다
— "⚠ Claude Code 외 **0개** 항목이 함께 바뀔 수 있습니다"(V-02), "✓ v**?**(으)로
설치되었습니다 / 확인됨(verified)"(V-03). 둘 다 **비가역 실행 직전·직후 화면**이라
값어치가 크다. ②좁은 창 폭은 대부분 잘 버틴다 — 30개 조합 전부 가로 오버플로 0이고,
읽을 수 없게 되는 화면은 **프로젝트 상세의 파일 미리보기 딱 하나**다(V-04, `@media` 3줄로 끝난다).
③폼을 열면 화면의 최강조 버튼이 "취소"가 된다(V-06).

**라운드1 변경이 만든 부작용은 1건 확인됐다** — 마켓플레이스에서 목업을 지우며 그 탭이
무엇인지 설명하는 유일한 문장까지 함께 사라졌다(V-11). PM이 우려한 "홈 카드 높이
들쭉날쭉"·"설정 칩 탭 제거 후 위치 파악 곤란"은 **캡처로 확인한 결과 발생하지 않았다**(기각 섹션 참조).

## U-21 재판정 (콘텐츠 최대 폭 규칙)

라운드1은 U-21을 **"R-02를 채택하면 자동 해소되므로 단독 수정하지 말 것"** 으로 보류했다.
**R-02가 기각됐으므로 그 전제가 사라졌다** — 지금 결정하지 않으면 이 항목은 근거 없이
영구 보류된다.

**패널 권고: 보류 유지(수정하지 않음).** 사유:
- 라운드1이 근거로 든 증상(설정 탭마다 폭이 널뛴다) 중 **가장 눈에 띄던 MCP 탭은 U-21 축소
  수정(`.mcp-list{max-width:1040px}`)으로 이미 완화**됐다.
- 남은 것은 V-13(정상 480px vs 에러 전체 폭)과 MCP 탭 내부(추가 폼 480 vs 목록 1040)뿐이고,
  **둘 다 상태 전환·폼 개폐 순간에만 보인다.**
- 전면 규칙화(폼형 560 / 목록형 1040을 전 화면에 적용)는 `settings.ts` 1,057줄과
  `styles.css` 다수 규칙을 동시에 건드리는 데 비해 체감 개선이 작다 — **50인 미만 내부
  도구 기준으로 지금 할 일이 아니다.**
- 대신 **새 화면을 만들 때만** "폼형 560 / 목록형 1040" 두 값 중 하나를 고른다는 규칙을
  구두로 세워 두는 것으로 충분하다(기존 화면 소급 적용 없음).

## 트레이드오프 (페르소나 간 충돌)

1. **발산형 "대시보드를 다시 설계하라" vs 파워유저·PM "정직성 수정과 재설계를 섞지 마라"**
   — 라운드1에서 PM이 R-01을 미룬 바로 그 충돌이다.
   → **권고: R-01′(축소판)로 봉합한다.** 재설계가 아니라 **표시 문자열 교체**이므로
   "정직성 수정"과 성격이 같아진다(둘 다 "화면이 아는 것을 말하게 한다"). 오히려
   U-23을 고치며 `home.ts`를 여는 김에 같이 하는 것이 싸다. 전면 재작성은 반대다.

2. **창폭 페르소나 "900px를 1급 시민으로" vs 조직 규모(50인 미만 내부 도구)**
   → **권고: 부분 채택.** `@media` 1개(V-04)만 넣고 전역 반응형은 도입하지 않는다.
   대신 R-06대로 **검증 폭을 늘려** 다음 회귀를 자동으로 잡는다. 규칙보다 관측이 싸다.

3. **상태정직성 "모르는 것은 모른다고 말하라" vs 파워유저 "경고를 늘리지 마라"**
   — V-02가 정면 사례다. `affected 0건`을 별도 경고로 분리하면 경고 종류가 하나 늘어난다.
   → **권고: 늘린다.** 단, `warnMultiple` 조건을 `> 1`로 좁히므로 **정상 경우의 경고는
   오히려 줄어든다**(affected 1건이면 아무 경고도 안 뜬다). 총 경고량은 감소한다.

4. **신입 "설명을 붙여라" vs 라운드1의 "목업을 지워라"**
   — V-11이 이 충돌의 산물이다(지우면서 설명도 지웠다).
   → **권고: 목업은 지우고 설명은 남긴다.** 두 문장이 한 블록에 있었던 것이 원인이므로,
   앞으로 UI를 삭제할 때 **삭제 대상이 설명 문장을 데리고 가는지** 확인한다.

## 잘 된 점 (다음 산출물의 기준)

1. **라운드1 수정이 실제로 먹혔다.** `r1__home__error.png` → `r1-final__home__error.png`는
   "지적 → 수정 → 실물 확인"이 한 바퀴 돈 교과서적 사례다. 하네스의 `verify()`까지
   함께 갱신해(`routes.mjs:46-51, 106-110, 155-159, 217-220`) **수정이 회귀하면 캡처가
   깨지도록** 만들어 둔 것이 특히 좋다 — 수정과 회귀 방어를 같은 커밋에서 끝냈다.
2. **`@media` 없이 760px까지 버티는 CSS.** 10개 라우트 × 3폭 = 30조합 전부 가로 오버플로
   0. `auto-fit minmax()`·`min-width:0`·`text-overflow:ellipsis`를 예외 없이 쓴 결과다.
3. **사용량 일별 상세 패널**(`r2__act__usage-daily-detail.png`)은 이 앱 조작 이후 화면의
   최고 수준 — 클릭한 행 바로 아래 인라인, 에이전트별 턴/토큰/비용 표, 툴 칩, 900px에서도
   무너지지 않음. 다른 상세 패널(dev-tools)을 고칠 때 여기를 베끼면 된다.
4. **자율업무 추가 폼**(`r2__act__task-add-form.png`)의 안내 밀도. 실행 주기의 기준 시점,
   타임아웃 범위, 첫 실행 지연 이유까지 전부 폼 안에 적혀 있어 문서를 볼 필요가 없다.
5. **파괴적 조작의 동의 설계가 문서와 코드에서 일치한다.** "전체 업데이트"를 결함으로
   올릴 뻔했으나 주석(`devTools.ts:239-262`)이 결정 이력과 그 이유(M1)를 정확히 남겨
   두어 리뷰가 자체 기각할 수 있었다. **주석이 오탐을 막은 사례**다.
6. **캡처 하네스의 확장성.** `stub.mjs`/`fixtures.mjs`가 잘 분리돼 있어 이번에 폭 3종
   캡처와 픽스처 변형 재현(`round2b.mjs`)을 각각 100줄 미만으로 붙일 수 있었다.
   V-02(`외 0개`)는 **픽스처를 바꿔 재현하지 않았으면 코드 읽기만으로는 확신할 수 없었던**
   지적이다.
