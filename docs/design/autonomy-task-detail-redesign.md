# 자율업무 상세보기 화면 재설계

대상: `malgn-vscode`(Tauri 데스크톱 앱) — `src/views/autonomousTasks.ts`의 `renderAutonomousTaskDetailView`(현재 1051~1121행). 등급: Standard.
이 문서 하나로 frontend-dev가 추가 질문 없이 구현할 수 있어야 한다. **이 문서는 설계 산출물이며 `src/**`·`src-tauri/**`는 수정하지 않았다.**

## 0. visual-designer 필요 여부

**생략 가능.** 이 화면은 신규 모듈이 아니라 기존 관리자성 내부 도구(맑은에이전트) 안의 기존 화면 하나를 재배치하는 작업이고, 사용자단이 아니라 개발자 본인이 쓰는 관리 화면이다. `src/styles.css`에 이미 확립된 토큰(`--color-*`)과 클래스 패턴(`.overview-card`, `.mcp-row`, `.plugin-entry-row`, `.badge-*`, `.state-block`)만으로 아래 설계가 전부 표현되며 새 색상·타이포·간격 스케일이 필요하지 않다(§6 토큰 매핑 참조). 신규 시각 요소는 결과 4종 배지뿐인데, 기존 success/danger/warn 토큰 3종 + 기존 archived 계열 중립 회색으로 커버되어 새 토큰도 0개다.

## 1. 정보 위계 판정

8~12개 정보 항목을 1차/2차/3차로 분류한다. 판정 기준: **"사용자가 이 화면을 여는 가장 흔한 두 가지 이유"** — ① 지금 상태 확인 후 즉시 조작(실행/중지) ② 왜 실패했는지 진단(이력 확인). 이 두 목적에 즉답하는 정보만 1차다.

| # | 항목 | 위계 | 근거 |
|---|---|---|---|
| 1 | 작업 이름 + 현재 상태(실행중/대기/중지) | 1차 | 화면 진입 즉시 "이게 뭐고 지금 어떤 상태인가"에 답하는 유일한 항목. 헤더에 항상 노출. |
| 2 | 다음 실행 예정 시각 | 1차 | "다음에 언제 도나"는 사용자가 실행 버튼을 누를지 말지 결정하는 근거. enabled=false면 "예정 없음"으로 즉시 알아야 한다(꺼진 걸 깜빡하고 방치하는 사고 방지). |
| 3 | 지금 실행 / 중지·재개 버튼 | 1차 | 이 화면에 들어오는 두 목적 중 하나가 "조작"이므로 항상 눈에 들어와야 한다. |
| 4 | 실행 이력 리스트(최근 N건) | 1차 | 이번 재설계의 핵심 요구사항. "왜 실패했나"에 답하는 유일한 항목이며 지금까지 화면에 없었던 것 자체가 결함이었다. |
| 5 | 프로젝트(경로/이름) | 2차 | 설정을 스캔할 때 확인하는 항목. 조작 결정에 직접 쓰이진 않지만 "이게 어느 프로젝트 것인지" 혼동 방지용으로 늘 필요하다 — 좌측 메타 블록에 상시 표시하되 헤더만큼 크지 않다. |
| 6 | 실행 주기(스케줄 요약) | 2차 | "다음 실행 시각"(1차)의 근거가 되는 상세 규칙. 시각을 이미 1차로 봤으면 대부분 안 봐도 되지만, 스케줄을 바꿀지 판단할 때 스캔한다. |
| 7 | 프롬프트 전문 | 2차 | **"프롬프트가 왜 1차가 아닌가"**: 프롬프트는 대개 길고(요구사항 원문에 "긴 텍스트"라는 언급은 없지만 실제 자율업무 프롬프트는 몇 문장~한 문단 이상이 흔함) 매 진입마다 정독할 대상이 아니라 "설정을 다시 확인/복붙하고 싶을 때" 스캔하는 참조 자료다. 다만 접어버리면(3차) 실패 원인이 "프롬프트가 이상해서"인 경우 진단이 느려지므로, 스크롤하면 바로 보이는 2차 박스로 둔다(접지 않음, 말줄임 없이 전문 표시하되 화면 하단 쪽에 배치). |
| 8 | 서브에이전트 지정 여부 | 2차 | 설정을 재확인할 때 보는 부가 정보. 없음(null)이 기본값이라 대부분 "지정 안 함"으로 채워질 것이므로 항상 눈에 띌 필요는 없다. |
| 9 | 타임아웃 값 | 2차 | 실패 원인이 타임아웃일 때(이력에 `timeout` 표시가 뜬 직후) 확인하러 오는 항목 — 이력을 먼저 보고 필요할 때 스캔하는 흐름이라 2차. |
| 10 | 마지막 실행 요약(stdout/stderr 꼬리) | 3차 | 이력 리스트의 각 항목이 로그 파일 경로를 제공하므로, 요약 500자는 "이력 리스트 항목을 펼쳤을 때"만 보이면 충분하다 — 항상 펼쳐두면 리스트가 장문 텍스트로 뒤덮여 정작 중요한 시각/결과 스캔을 방해한다. |
| 11 | 실행 로그 파일 경로 | 3차 | 파일시스템 경로는 대부분의 진단에서 "복사해서 터미널에 붙여넣는" 용도이지 눈으로 스캔하는 정보가 아니다. 이력 항목별로 접어두고 클릭 시 펼치거나 복사 버튼만 노출한다. |
| 12 | 수정/삭제 버튼 | 3차(조작이지만 저빈도) | 매번 쓰는 액션이 아니고 삭제는 파괴적이라 오히려 눈에 덜 띄어야 안전하다(§3). |

## 2. 레이아웃 구조 — 대안 비교

**대안 A: 좌우 2컬럼(사용자 제시 레퍼런스 방식)** — 좌측에 메타(상태/프로젝트/스케줄/타임아웃), 우측에 프롬프트+이력. 장점: 이 앱 창은 사이드바(216px) 제외 콘텐츠 영역이 통상 1000px 이상 확보되어(기존 `.mcp-list`가 1040px, `.project-grid`가 260px 카드 auto-fill로 이미 넓은 폭을 전제) 2컬럼이 여백 낭비 없이 들어맞는다. 메타 정보(짧은 값들)와 이력 리스트(세로로 길어질 수 있는 목록)의 "정보 밀도가 다른 두 블록"을 나란히 둬 각자 자기 스크롤 리듬을 가질 수 있다.
**대안 B: 단일 컬럼 카드 스택(현재 방식의 개선판)** — 헤더 → 액션 → 상태 요약 카드 → 이력 카드 → 프롬프트 카드를 위에서 아래로 순서대로 쌓는다. 장점: 창 폭에 관계없이 항상 안전하고 구현이 단순하다. 단점: 이력 리스트가 길어지면(20건) 프롬프트·설정 정보가 스크롤 밖으로 밀려나 2차 정보 접근성이 떨어지고, 이 앱의 확보된 가로 폭을 전혀 활용하지 못해 세로로만 계속 길어지는 "허접해 보였다"는 원래 불만(여백·위계 부재)의 세로판 재현이 될 위험이 있다.

**선택: 대안 A(2컬럼).** 근거: ① 이 프로젝트 창은 이미 1000px대 콘텐츠 폭을 다른 화면(`.mcp-list` 1040px)에서 전제하고 있어 2컬럼이 어색하지 않다 ② 사용자가 명시적으로 제시한 레퍼런스와 구조가 일치해 기대와 어긋나지 않는다 ③ 1차 정보(상태/다음 실행/버튼)를 좌측에 고정해 두면 우측 이력 리스트를 아무리 스크롤해도 조작 지점을 잃지 않는다(단일 컬럼은 이 보장이 없다).

## 3. 액션 버튼 배치와 위계

- **위치**: 헤더 우측(제목·상태 배지와 같은 줄, `.detail-header`의 오른쪽 정렬 영역). 사용자 제시 레퍼런스와 동일하게 "지금 실행"을 헤더 우측 상단에 프라이머리로 고정한다. 현재 구현처럼 제목 아래 별도 줄에 왼쪽 정렬로 다닥다닥 붙이지 않는다.
- **프라이머리(1개)**: "지금 실행" — `.btn-primary` 유지. 이 화면에 들어오는 즉시 실행 가능해야 하는 유일한 능동 액션이다.
- **세컨더리**: "중지 / 재개"(토글) — 헤더 우측, 프라이머리 버튼 바로 왼쪽에 `.btn`(기본 스타일)으로 배치. 실행 여부와 별개로 자주 쓰는 조작이라 헤더에 남기되 시각적으로 프라이머리보다 가볍게.
- **수정** — 좌측 컬럼(상태 메타 블록) 맨 아래로 이동. 헤더에서 빼는 이유: 설정을 "확인하다가 고치고 싶을 때" 접근하는 동선이 자연스러워, 설정이 모여 있는 좌측 블록 하단에 두면 "그 정보를 보다가 누르는" 위치가 된다. 헤더 혼잡도도 낮아진다.
- **삭제** — 좌측 컬럼 맨 아래, 수정 버튼과 시각적으로 분리(위 8px 여백 + `border-top: 1px solid var(--color-hairline)` 구분선)해 배치하고 텍스트 색을 `var(--color-danger)`로 유지(기존 구현 방식 유지). 파괴적 액션은 프라이머리 동선(헤더)에서 최대한 멀리, 그리고 실수로 "중지"나 "수정"과 나란히 눌리지 않도록 구분선 아래 단독 배치한다. 클릭 시 기존 `handleDeleteTask`의 확인 절차를 그대로 유지(변경 없음).
- **여백(px)**:
  - 헤더 내부 액션 버튼 그룹: 버튼 간 `gap: 8px`(기존 `.settings-form-actions`의 `gap: 8px`와 동일 — 새 규칙 불필요, 헤더 우측 정렬 컨테이너에만 재사용).
  - 헤더와 그 아래 2컬럼 영역 사이: `margin-top: 20px`(섹션 간 규칙, §5와 통일).
  - 좌측 컬럼 하단 수정 버튼 위 구분선: `padding-top: 16px; margin-top: 16px; border-top: 1px solid var(--color-hairline)`.
  - 수정 버튼과 삭제 버튼 사이 세로 간격: `gap: 8px`(세로 stack이면 `flex-direction: column; gap: 8px`).

## 4. 실행 이력 리스트 설계 (핵심)

### 4-1. 리스트 아이템 1건의 구조

한 줄(행) 안에 좌→우 순서로 배치(참고: 기존 `.mcp-row`/`.marketplace-plugin-row` 패턴 — flex row, 양끝 정렬, hairline 구분선):

```
[결과 아이콘+배지]  시작 시각(상대시각)          소요시간        [세부 보기 ▾]
```

- **1열: 결과 배지** — 아이콘 + 짧은 라벨(예: "✓ 성공"). 고정 폭(아이콘류라 좁게).
- **2열: 시작 시각** — 상대시각 우선 표기(§4-3). `flex: 1`로 남는 공간을 차지.
- **3열: 소요시간** — 우측 정렬, `초` 단위 반올림 값을 기본으로 하되 60초 이상이면 "분초"로 조합(§4-4).
- **4열: 세부 보기 토글** — 클릭하면 행 아래로 펼쳐져 요약(summary, 최대 500자, `white-space: pre-wrap`)과 로그 파일 경로(§4-5)를 보여준다. 기본은 접힘 상태(정보 위계 판정 §1의 10·11번이 3차이기 때문).

행 높이는 접힌 상태에서 한 줄(약 36~40px 상당 — 기존 `.mcp-row`/`.marketplace-plugin-row`와 동일한 리듬), 펼치면 요약 블록만큼 늘어난다.

### 4-2. 결과 4종의 시각 구분

| result | 아이콘 | 라벨 | 배경/텍스트 토큰 |
|---|---|---|---|
| `success` | ✓ | 성공 | 배경 `var(--color-success-soft)`, 텍스트 `var(--color-success-text)` |
| `failed` | ✕ | 실패 | 배경 `var(--color-danger-soft)`, 텍스트 `var(--color-danger)` |
| `timeout` | ⏱ | 타임아웃 | 배경 `var(--color-warn-bg)`, 텍스트 `var(--color-warn-text)`, 테두리 `var(--color-warn-border)` |
| `aborted` | ⊘ | 중단됨(앱 종료) | 배경 `#f3f4f6`, 텍스트 `var(--color-ink-muted)` — 기존 `.badge-archived`와 동일한 중립 회색 조합을 재사용(신규 토큰 없음) |

새 CSS 변수는 만들지 않는다 — 기존 success/danger/warn 3종 + 기존 archived 중립 회색 1종으로 4개 결과를 전부 표현할 수 있다. 구현 시 `.badge` 베이스 클래스에 `.badge-run-success` / `.badge-run-failed` / `.badge-run-timeout` / `.badge-run-aborted` 4개 modifier 클래스를 추가하는 것을 권장(기존 `.badge-active`/`.badge-archived`/`.badge-unknown` 命名 패턴과 동일).

### 4-3. 시각 표기 방식

- **오늘 안**: "오늘 오후 7:32" (사용자 제시 레퍼런스와 동일한 상대 표기, 로컬 타임존 12시간제).
- **어제**: "어제 오후 9:01".
- **그 외(2일 이상 전)**: 절대 날짜로 전환 — "9/14 오후 9:00" (연도는 올해가 아닐 때만 추가: "2025/9/14 오후 9:00"). 이유: "3일 전" 같은 상대 표기가 계속 누적되면 정확한 날짜 감각을 잃기 쉽고, 로그 파일이 `YYYY-MM-DD` 디렉터리로 저장되므로(§ 백엔드 계약) 사용자가 로그를 직접 찾아갈 때도 절대 날짜가 실사용에 더 맞다.
- 판정 기준은 "달력 날짜가 같은가/전날인가"이지 "24시간 이내"가 아니다(자정 직후 실행 건이 "어제"로 잘못 표기되는 것을 방지 — 달력 날짜 비교로 오차를 없앤다).
- `title` 속성(hover 툴팁)에 항상 RFC3339 원본 절대시각을 넣어 상대/축약 표기의 손실을 보완한다.

### 4-4. 소요시간 표기

- `durationMs < 60_000`: `${Math.round(durationMs/1000)}초`.
- `durationMs >= 60_000`: `${분}분 ${초}초` (예: "60분 00초"). 분만 표시하고 초를 버리면 "타임아웃 60분"과 "59분 40초 성공"을 리스트에서 구분하기 어려워지므로 초까지 표기한다.

### 4-5. 로그 파일 경로 처리

- 접힌 기본 상태에서는 노출하지 않는다(§1 3차 판정).
- "세부 보기" 펼침 시: 경로 문자열을 `font-family: ui-monospace` 고정폭으로 한 줄 표시 + 클립보드 복사 버튼(`.btn-sm`, 라벨 "경로 복사"). 파일을 앱이 직접 열어주는 기능은 범위 밖(백엔드에 그런 커맨드가 없다) — 복사까지만 지원하고 사용자가 터미널/파인더에 붙여넣는다.
- 긴 절대경로가 레이아웃을 밀지 않도록 `overflow: hidden; text-overflow: ellipsis; white-space: nowrap` + hover 시 `title`로 전체 경로 노출(기존 `.mcp-row-target` 처리 방식과 동일).

### 4-6. 상태 4종 (빈 / 로딩 / 에러 / 더 보기)

이력은 `autonomy_task_history(projectPath, taskId, limit?)`를 화면 진입 시 **비동기 별도 호출**로 가져온다(설정/런타임 조회와 분리된 3번째 IPC — 결정 2의 "커맨드를 갈라 두면 경계가 타입으로 강제된다" 원칙과 일관되게, 이력 로딩 실패가 설정/런타임 표시를 막지 않아야 한다).

| 상태 | 트리거(주체+이벤트) | 표시 |
|---|---|---|
| 로딩 | 상세 화면 진입 시, `autonomy_task_history` 프라미스가 아직 resolve되지 않은 동안 | 이력 카드 내부에 기존 `.state-block` 패턴 재사용, 제목 "불러오는 중…" (설정 로딩 시 쓰는 문구와 통일) |
| 빈 상태 | 호출은 성공했으나 배열 길이 0 (한 번도 실행 안 됨, 또는 로그 보존기간 경과로 전부 스윕됨) | "아직 실행 이력이 없습니다. '지금 실행'을 눌러 첫 실행을 시작하세요." + 텍스트 안에 실행 버튼 위치를 가리키는 안내만(별도 CTA 버튼 중복 배치는 하지 않음 — 프라이머리 버튼은 헤더에 이미 있다) |
| 에러 | 호출이 `Err`로 reject (로그 디렉터리 없음/읽기 실패) | 기존 `.alert` 배너 재사용: "실행 이력을 불러오지 못했습니다 — {오류 메시지}" + "다시 시도" 버튼(`autonomousTasks.ts`의 기존 재시도 패턴과 동일하게 상태를 다시 fetch). 이 실패가 좌측 메타 블록이나 프롬프트 표시를 막지 않는다(이력 카드 안에만 국한). |
| 더 보기(기본 20건 초과) | 사용자가 "더 보기" 버튼 클릭 시 | 최초 호출은 `limit` 생략(백엔드 기본 20건). "더 보기" 클릭 시 `limit`을 40 → 60 …으로 20씩 늘려 재호출하고 리스트를 교체 렌더(추가 append가 아니라 전체 재조회 — 백엔드가 항상 "최신순 상위 N건"을 돌려주는 계약이므로 누적 append보다 안전하다). 반환 건수가 요청한 `limit`보다 적으면(더 없음) "더 보기" 버튼을 숨긴다. |

## 5. 여백·간격 규칙 (px)

- 헤더(`.detail-header`) 하단 여백: `margin-bottom: 20px` (기존 18px에서 소폭 확대 — 액션 버튼이 헤더로 이동해 그 아래 2컬럼과의 시각적 분리를 조금 더 확보).
- 2컬럼 그리드 자체의 컬럼 간격(gap): `24px`.
- 좌측 메타 카드 내부 패딩: `20px`(기존 `.overview-card`의 `padding: 20px` 그대로 재사용).
- 좌측 메타 카드 내 섹션(상태/프로젝트/반복/타임아웃/서브에이전트) 간 구분: 기존 `.overview-section + .overview-section`의 `margin-top: 18px; padding-top: 18px; border-top: 1px solid var(--color-hairline)` 그대로 재사용.
- 우측 프롬프트 카드 내부 패딩: `20px`(좌측과 동일 리듬 유지).
- 프롬프트 카드와 기록 카드 사이 간격: `20px`(세로 stack이면 `margin-top: 20px`).
- 기록 카드 내부 패딩: `16px`(리스트형 카드는 `.mcp-add-card`류보다 살짝 좁게 — 리스트 아이템 자체가 좌우 여백을 가지므로 카드 패딩을 20px까지 줄 필요는 없다).
- 이력 리스트 아이템 간 간격: 구분선 방식(`gap` 아님) — `padding: 10px 0; border-bottom: 1px solid var(--color-hairline)`, 마지막 아이템은 `border-bottom: none` (기존 `.marketplace-plugin-row` 패턴 그대로).
- 이력 리스트 "더 보기" 버튼 위 여백: `margin-top: 12px`, 가운데 정렬.
- 펼쳐진 세부 보기 블록의 상단 여백: `margin-top: 8px`, 좌측 들여쓰기 `padding-left: 4px`(배지 열과 시각적으로 정렬).

## 7. 핵심 시나리오의 비정상 흐름 정리 (자기검증용 요약)

- **시나리오: 상세 화면 진입** — 정상(설정+런타임+이력 3건 모두 로드 성공) / task를 찾을 수 없음(기존 처리 유지) / 설정 로딩 중(기존 `.state-block` 유지) / 설정 조회 에러(기존 `.alert` 유지) / **이력만 별도로 에러**(§4-6, 다른 블록에 전파되지 않음).
- **시나리오: 이력 리스트 조회** — 로딩 / 빈 상태(0건) / 에러(reject) / 더 보기(20건 초과) — §4-6에 4종 모두 명시.
- **시나리오: 지금 실행 클릭** — 기존 `handleRunNow` 로직·문구("실행 중…"/"요청 중…") 변경 없음. 실행 완료 후 이력 리스트가 최신 1건을 반영하려면 `autonomy-task-updated` 이벤트 수신 시(또는 폴백 폴링 시) 이력도 함께 재조회하도록 frontend-dev가 구현 — **주체+이벤트**: "런타임 상태 갱신 이벤트 수신 시, 이력 목록도 재조회한다."
- **CTA 목적지 명시**: "지금 실행"→같은 화면 내 상태 갱신(이동 없음). "중지/재개"→같은 화면 내 상태 갱신. "수정"→기존 `openTaskFormModal(task)`(범위 밖, 변경 없음). "삭제"→성공 시 `navigate('#/tasks')`(기존 유지). 이력 "더 보기"→같은 화면 내 리스트 확장. 이력 "세부 보기"→같은 행 안에서 펼침(이동 없음). "경로 복사"→클립보드(이동 없음, 화면 밖 부작용 없음).

## 8. 측정성 메모

- "다음 실행 예정 시각" = 서버(런타임 상태)가 내려주는 `nextRunAt`을 그대로 표시 — 프론트가 재계산하지 않는다(자율업무 런타임 설계 §2의 정본을 그대로 신뢰).
- "오늘/어제/그 외" 판정 = "실행 시작 시각의 로컬 달력 날짜가 오늘의 로컬 달력 날짜와 같은가"로 정량 비교(§4-3), "느낌상 최근"이 아니다.
- "더 보기 버튼 숨김" 트리거 = "이번 조회에서 반환된 배열 길이가 요청한 `limit`보다 작다"로 정량 판정, 별도의 "총 개수" API 없이도 정확하다.
