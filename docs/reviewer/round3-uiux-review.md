## A. V-03 최종 판정 — 실재인가 픽스처 허구인가

### A-1. 백엔드가 실제로 만들 수 있는 조합 (Rust 정독 결과)

`check_tool_version()`은 `Option<String>`을 돌려주고, **spawn 실패이거나 stdout이 비고 (종료코드≠0 또는 stderr가 빔)이면 `None`**이다(`src-tauri/src/dev_tools/process.rs:316-339`).

| # | 경로 | `version_before` | `outcome` / `verified` | 근거 |
|---|---|---|---|---|
| 1 | **신규 설치 성공** (`run_install_plan`, exit 0 + 설치 후 버전 재조회 성공) | **`None`** (하드코딩) | `Updated` / `true` | `actions.rs:253-259`(Outcome), `actions.rs:291-292`(`version_before: None`) |
| 2 | 이미 설치된 도구 업데이트 성공 | `Some("2.0.68")` | `Updated` / `true` | `actions.rs:52`, `88-97` |
| 3 | **설치돼 있으나 `--version` 조회가 실패**한 도구를 업데이트 | **`None`** | `Updated` / `true` | `actions.rs:52-56`(`unwrap_or_default()`로 `""`), `process.rs:326-338` |
| 4 | 실행은 성공했는데 사후 버전 조회 실패 | 무관 | `UnknownAfter` / **`false`** | `actions.rs:103-108`, `260-264` |

**결정적 사실 하나**: `Updated`(+`verified:true`)는 **`normalized_after`가 `Some`일 때만** 만들어지고, `normalized_after`는 `version_after`에서 파생된다(`actions.rs:80`, `237`). 즉 **버전을 모르면서 `Updated`·`verified:true`인 결과는 백엔드에서 만들어질 수 없다.**

### A-3. 결론과 처방 — **방향이 반대다**

라운드2는 "패널이 틀리고 토스트가 맞다"고 봤지만, **실제로 자주 벌어지는 경로에서는 패널이 맞고 토스트가 틀린다.** 따라서 라운드2가 제안한 `installedFresh`를 `tool.installed === false`로 바꾸는 처방은 **채택하지 않는다** — 그 값은 실행 후 `loadDevTools()`로 갱신되므로(`devTools.ts:151-157`) 목록이 새로고침되는 순간 **결과 패널의 동사가 "설치"에서 "업데이트"로 뒤바뀌는** 새 버그를 만든다. 결과 객체(불변 스냅숏)를 기준으로 두는 지금 구조가 옳다.

**권고(1~2줄)**: `notifyOutcome()`이 패널과 같은 규칙을 쓰게 한다.
```
case 'updated': { const fresh = !result.versionBefore;
  showToast(`${tool.name}: v${result.normalizedAfter ?? result.versionAfter}(으)로 ${fresh ? '설치' : '업데이트'}되었습니다`); }
```
덧붙여 `devTools.ts:563-564`의 `${versionBefore ?? '?'} → ${versionAfter ?? '?'}`는 **신규 설치 때 실제로 `? → 2.0.68`로 찍힌다**(경로 1에서 `versionBefore`가 항상 `None`). 같은 줄에서 `신규 설치: 2.0.68`로 분기하면 `?`가 사용자 눈에 닿는 마지막 자리가 없어진다.

1. **파워유저 "사이드바 키보드는 지금 고쳐야 한다" vs 조직 규모 "50인 미만 사내 도구에 접근성 과투자 아닌가"**

   → **권고: 이번엔 `clickable()`로 닫고, R-07은 "다음에 사이드바를 손댈 때"의 방향으로 기록한다.** 마지막 라운드에 CSS 리셋을 동반한 구조 변경을 넣으면 검증 부담이 이 라운드가 얻은 안정성보다 커진다.

2. **"삭제로 해결한 것"이 많다.** 목업 토글 2개, 라벨 10곳, 칩 탭, 빈 세그먼트 — 기능 추가 없이 화면이 정직해졌다. 내부 도구에서 가장 값싼 개선 방식이다.
3. **`clickable()`·`loadingBlock()`·`errorBlock()`·`pickState()` 승격이 실제로 재사용됐다.** 라운드2에서 만든 헬퍼가 이번 라운드 R3-01의 처방까지 그대로 재사용 가능하다는 점이 그 증거다.
4. **주석이 리뷰 오탐을 두 번 막았다.** 라운드2의 "전체 업데이트" 오탐(`devTools.ts:239-262` 주석)에 이어, 이번엔 `actions.rs:205-213`의 "claimed ≠ verified를 설치에도 적용한다" 주석이 V-03 판정을 빠르게 확정시켰다.
5. **백엔드가 UI보다 먼저 정직했다.** `UnknownAfter`·`verified:false`·`local_date_key`처럼 **모르는 것을 모른다고 말하는 타입과 함수가 Rust에 이미 있었다.** 3라운드의 UI 수정은 상당 부분 "백엔드가 이미 아는 것을 화면이 따라잡는" 작업이었다 — 다음 기능도 이 순서(백엔드에 정직한 타입 → UI가 그대로 표시)를 유지할 것.

## 총평 — 지금 멈춰도 되는가

**멈춰도 된다. 단, A그룹 3건(약 15줄)을 넣고 멈추는 것을 권고한다.**

세 라운드의 목적은 "이 앱이 자기 상태를 정직하게 말하게 한다"였고, **그 목적은 달성됐다.** 착수 전에는 모든 조회가 실패한 화면이 `0개 / 0/7 / 없음`을 사실로 단정했고 화면 곳곳에 저장되지 않는 목업이 섞여 있었다. 지금은 7개 위젯이 실패를 실패라고 말하고 그 자리에서 다시 시도할 수 있으며, 목업 UI는 0개이고, 비가역 실행 직전 화면은 무엇을 실행하는지·무엇이 함께 바뀌는지·모르면 모른다고 말한다. **후퇴는 없다** — 라운드2가 라운드1의 후퇴 1건을 잡았고, 이번 라운드는 라운드2가 만든 후퇴를 찾지 못했다(회귀 점검 5항목 전부 통과, 캡처 121장 pageerror 0).

남은 두 Major는 성격이 다르다. **R3-02는 제품이 아니라 리뷰 도구의 결함**이고, **R3-01은 "라운드2가 시작한 일의 마지막 한 칸"**이다 — 셋째 라운드에 걸쳐 같은 패턴("고쳤는데 한 칸을 덜 발랐다")이 반복된 만큼, 이번에는 그 한 칸을 채우고 끝내는 것이 이 3라운드 서사에 맞는 마무리다. 둘 다 합쳐 11줄이고 검증도 이미 있는 하네스 재실행으로 끝난다.

반대로 **더 벌리지 말아야 할 것**도 분명하다. U-21(콘텐츠 폭 규칙), R-02(설정 통합), R-07(`<button>` 시맨틱 전환), 전역 반응형은 전부 "지금 문제가 아니라 코드베이스를 계속 키울 때의 문제"다. 50인 미만 사내 도구에서 지금 화면 품질은 **다음 기능을 얹기에 충분히 단단하다** — 특히 `dom.ts`의 공용 헬퍼 4종과 캡처 하네스가 남아, 다음에 화면을 추가하는 사람이 같은 실수를 반복하지 않을 도구를 이미 갖췄다.
