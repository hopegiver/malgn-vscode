## 페르소나별 관점
### 자격증명 보관·전송 경로 감사자 — 🟢 Green
- settings.json 쓰기 경로·백업·목적지 선검사가 바뀌지 않았다. 새 상태는 이미 화면에 보이는 8자 prefix뿐이다. 프론트 계약에 추가된 것은 bool 하나다. 테스트가 상태 객체에 키 원문이 없음을 단언한다.

### Tauri 런타임 스레드·락 규율 — 🟢 Green(Nit 1)
- 새 락이 없고 기존 순서에 역방향 획득도 없다. 새 쓰기 두 곳은 stale 확인을 거치지만, 확인과 쓰기가 분리된 N-7 패턴을 이어받았다(N-7 확장). 영향은 재연결 경합 한 번에 표시가 잠깐 틀리는 정도다.

### claimed vs verified — 🟢 Green(Nit 2)
- 재발급 토스트의 성공 근거가 "파일에 키가 있음"에서 "키가 바뀌었다는 관측"으로 바뀌었다. 직전 회차에 RV-09로 재현한 거짓 성공을 같은 모양의 입력으로 다시 넣으면 실패 토스트가 나온다. 개발자 수치(941·46)는 직접 실행해 일치를 확인했다. "수정 전 실패" 주장은 TS는 실측, Rust는 변이로 대체 확인했다.
- 하네스·캡처는 이번에도 관측하지 않았다(N-13). 변이 1종이 살아남았다(N-14).

### 화면 상태 정직성 — 🟢 Green(Nit 2)
- 일시 오류가 판정을 지우지 않는다. 거절하지 않았는데 "거절"이라고 말하지도 않는다. "재확인 필요"가 사실("아직 다시 확인하지 못했습니다")만 말하고 일시 원인을 꼬리에 붙인다. 남은 것은 죽은 분기의 문구(N-11)와 재시작 한계(N-12, 수용)다.

## 트레이드오프
- **화면 정직성 vs 영속 상태 금지(N-12)**: 재시작 직후 공백을 없애려면 폐기 판정을 디스크에 남겨야 한다. 그러면 "앱은 허브 판정의 캐시를 영속하지 않는다"는 설계와 부딪히고, 캐시가 오래돼 생기는 반대 오류도 새로 생긴다. 지금 문구는 단정하지 않는다("수신은 아직 확인하지 않았습니다 + 마지막 점검 실패"). → 현행 유지를 권고한다.

## 잘 된 점
- 직전 권고 ①(엔진 `revoked_prefix`)과 ②(프론트 masked 변화 비교)를 **둘 다** 넣었다. 그래서 화면 회귀와 토스트 거짓을 서로 다른 층에서 독립적으로 막는다.
- 해제 조건을 dispatch 한 곳에서 "성공 응답이 ConfirmRequired가 아님"으로 정의했다. "GET 실패는 여기에 오지 않는다"는 사실을 주석과 테스트가 함께 고정한다. 종료 조건 4종(a~d)을 한 테스트 묶음으로 단언한 점도 좋다.
- 비일시 실패를 따로 처리하지 않고 기존 `failed_from` 경로에 맡겼다. 새 분기를 최소로 줄였다.
- 테스트가 "확인창을 다시 띄우지 않는다"(`!confirm_required`)와 "거절이라고 말하지 않는다"까지 단언한다. 상태값뿐 아니라 사용자가 보게 될 행동과 문구를 고정한다.
