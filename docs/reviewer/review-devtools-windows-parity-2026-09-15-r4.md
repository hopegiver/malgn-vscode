## 2. 신규 지적

### V1 🟠 Major — `/bin/cat` 테스트가 Windows에서 공허하게 초록이다

| 항목 | 내용 |
|---|---|
| **위치** | `src-tauri/src/dev_tools/process.rs:478-495` (`stdin_is_null_so_a_reading_process_fails_fast_instead_of_hanging`) |
| **확인방법** | `git show d906867:src-tauri/src/dev_tools/process.rs` 470-500 Read + spawn 실패 조기반환 경로(`run_process_with_timeout_cancellable`, 같은 파일 241-253) Read |
| **문제** | 이 커밋은 `/bin/echo`·`/bin/sleep`·`/bin/pwd` 3건을 `#[cfg(unix)]`로 게이팅했다. 그런데 같은 파일의 **네 번째 Unix 절대경로 테스트인 `/bin/cat`(`:484`)** 은 게이팅도, Windows 등가물도, 심지어 `spawn_error` 단언도 없다. Windows에서는 spawn이 실패해 `spawn_error: Some(..)` / `timed_out: false` / `elapsed ≈ 0`이 되고 → **두 단언이 모두 통과한다.** 즉 windows-latest의 `334 passed` 안에 **아무것도 검증하지 않은 초록 1건**이 섞여 있다. stdin=null(설계 부록 B.1)은 Windows에서도 실재하는 프로덕션 불변식인데(자식이 stdin을 읽으면 타임아웃까지 매달린다) Windows 커버리지는 0이고, "초록"이 그 공백을 가리고 있다 |
| **왜 Major인가** | 이 커밋의 존재 이유가 "CI 초록의 정직성 회복"이다. 그런데 남은 공허한 초록이 **바로 그 파일, 바로 그 유형**이다. 8건 조사 방법론(로그에 뜬 것만 처리)의 구조적 사각 — 조용히 통과하는 테스트는 로그에 뜨지 않는다 |
| **처방** | ① **최소(1줄)**: 해당 테스트에 `assert!(output.spawn_error.is_none(), "…")` 추가 — 공허한 초록이 즉시 빨강이 되어 문제가 드러난다. ② **권장**: `#[cfg(unix)]` 게이팅 + Windows 등가물 신설. 인자 없이 stdin을 읽는 표준 유틸은 `C:\Windows\System32\findstr.exe`(`["/R", "."]`) 또는 `sort.exe` — null stdin이면 즉시 EOF로 빠르게 종료해 동일 취지를 검증한다. ③ 재발 방지: `git grep -n '"/bin/\|"/usr/bin/' src-tauri/src` 로 테스트 코드의 Unix 절대경로 리터럴을 전수 훑고 각각 게이팅 여부를 확인 |

### V2 🟠 Major — winget 필드 승격의 값을 절반만 회수했다(`Some` 주입 테스트 0건)

| 항목 | 내용 |
|---|---|
| **위치** | `src-tauri/src/dev_tools/install_resolver.rs:503, 532, 588, 630`(전부 `winget: None`) + `src-tauri/src/dev_tools/runners.rs:230-240`(Mac에서 None인 것만 확인) |
| **확인방법** | `git show d906867:.../install_resolver.rs \| grep -n "winget\|Winget"` 전수 + `install_candidates(Gh)` 순서(`install_resolver.rs:120-137`) Read + `install_prefix_writable_always_passes_for_winget`(`runners.rs:209-216`) Read |
| **문제** | 이 커밋은 설계 §B.2/C.3.1의 "기존 테스트 0개 수정" 원칙을 깨는 **대가를 치르고** 주입 가능성을 얻었다. 그런데 실제로 주입한 값은 **`None`뿐**이다. Windows에서 실제로 돌아갈 경로 — gh가 winget 러너로 `Run`이 되고 `installer_label: "winget"`, argv에 `GitHub.cli`가 실리는 것, 즉 **설계 §B.1/B.2의 핵심 약속** — 을 검사하는 테스트는 여전히 0건이다. 현재 있는 것은 "러너가 전부 없으면 Manual"이라는 **음성 방향뿐**이다 |
| **핵심** | 이 테스트는 **지금 당장 macOS에서 플랫폼 독립적으로 돌아간다.** `install_prefix_writable`은 Winget에 대해 무조건 true이고(위 테스트가 그 성질을 이미 고정), `RUN_WINGET_INSTALL_GH.args`는 `Arg::Lit` 전용이라 `resolve_args`가 항상 Ok다(`install_resolver.rs:181-184` 주석). 즉 파일시스템·플랫폼에 전혀 의존하지 않는다. **약 12줄이면 된다** |
| **처방** | `install_resolver.rs` 테스트 모듈에 추가: `ResolvedRunners { brew: None, npm: None, pnpm: None, winget: Some(r"C:\Users\x\AppData\Local\Microsoft\WindowsApps\winget.exe") }` → `resolve_install_plan(ToolId::Gh, &runners)`가 `InstallResolution::Run { runner_path, argv, installer_label: "winget", .. }`이고 argv에 `"GitHub.cli"`가 포함되는지 단언. 이러면 "Windows에서 gh는 winget으로 설치된다"가 **실기 배포 전에 처음으로 자동 검사된다** |

## 4. PM이 특별히 물은 4가지

### Q1. 테스트를 통과시키려고 검증 능력을 잃은 자리가 있는가
**있다 — V1(새로 생긴 공허한 초록), V2(회수 안 한 자리), V4(불필요하게 잃은 자리). 그러나 커밋 전체로는 순증이다.** 상세는 §1 표.
- 기대값만 바꿔 통과시킨 것: **1건뿐이고, 그 판단이 옳다.** 구현자의 "로직은 옳았고 틀린 건 테스트 기대값"은 독립 확인 결과 **참**이다 — 설계 §D.5 계약은 "프로세스 PATH만 본다"이지 "항상 못 찾는다"가 아니다.
- 덮은 것: `#[ignore]` 2건 중 **1건만 정당**(V4).
- 약해진 것: 항진 단언 1건(V6②). 반대로 **원래 없던 분기를 새로 덮은 것이 2건**(diagnostics true 분기, Windows current_dir 고정).

### Q2. `PING.EXE -n 31 127.0.0.1`은 적절한가 / 무엇이 검증됐나 / 사내 PC에도 같은가

**적절하다. 그리고 구현자의 "가정"은 CI 초록으로 가정 이상이 됐다.**

**실제로 검증된 것 (3가지, 전부 프로덕션 코드):**
1. `C:\Windows\System32\PING.EXE` 절대경로 spawn 성공 — 실패했다면 `spawn_error`가 채워지고 `timed_out: false`가 되어 **첫 단언이 깨진다**.
2. 자식이 500ms를 넘겨 생존 — 타임아웃 분기에 실제로 진입했다.
3. **`force_kill_process_group`의 Windows 분기(`child.kill()` → `TerminateProcess`, `child.wait()`)가 자식을 실제로 죽였다.** 이게 핵심이다 — `child.wait()`는 **블로킹**이므로(`process.rs:160-165`) 종료가 안 됐다면 PING의 남은 ~30초를 그대로 기다려 `elapsed < 5s` 단언이 깨진다. 즉 이 테스트는 "타임아웃 감지"만이 아니라 **Windows kill 경로의 실효성**을 검사하며, 이번 CI가 그 경로의 **최초 실증**이다.

**아직 검증되지 않은 것:** ① 승격된 손자 프로세스(winget → msiexec) 정리 — 2라운드 N4가 이미 "구조적으로 불가"로 기록했고 변함없다. ② `exit_code.is_none()`은 항진(V6②)이라 아무것도 보태지 않는다.

**사내 PC 일반화 — 부하 요소 3개가 모두 머신 무관하다:** PING.EXE는 모든 표준 Windows 구성에 있고, **루프백 ping은 네트워크 정책과 무관**하며(ICMP가 차단돼도 실패 응답 대기로 500ms는 넘긴다 — 이 테스트가 필요로 하는 것은 "500ms 이상 생존"뿐이라 어느 쪽이든 성립), `TerminateProcess`는 자기 자식에 대해 권한 문제가 없다. **단, GitHub `windows-latest`는 AV/EDR·그룹정책이 없는 데이터센터 VM이다** — 사내 PC의 EDR이 자식 종료를 지연·차단하는 시나리오는 이 테스트로 배제되지 않는다.
→ **결론: 테스트 자체의 이식성은 높다. "사내 PC에서도 kill이 동작한다"는 실기 검증 항목으로 남긴다.**

### Q3. winget 캐시 승격이 3차까지의 판정을 뒤집는가 (특히 N2·M1)

**뒤집지 않는다. 세 방향 모두 코드로 확인했다.**

| 대상 | 판정 | 근거 |
|---|---|---|
| **N2(프리뷰 신뢰도)** | **무관 — 뒤집지 않음** | `winget_preview_is_reliable`는 `Runner` 값만의 순수 함수이고 러너 **경로**를 전혀 보지 않는다. 캐시 여부와 독립. gh가 "전체 업데이트" 배치에서 빠지는 성질(`devToolsApi.ts`의 `previewReliable===true && affected.length===1`)도 그대로 |
| **M1(분류 라우팅)** | **무관 — 뒤집지 않음** | M1은 **업데이트 경로**의 `classify_install_method_windows` → `UPDATE_TABLE` lookup 문제다. 그 경로는 `ResolvedRunners`를 **아예 거치지 않는다** — `perform_update` → `resolve_plan` → `resolve_runner_path` 직접 호출이고, `runners.rs:30-35` 주석이 그 이유(`self_binary_path` 인자가 필요해 캐시 그릇의 계약과 다름)를 명시한다. 게다가 Wrangler의 install 후보는 Pnpm/Npm이라 winget 축과 만나지 않는다 |
| **새로 생기는 것 = staleness 하나** | **수용 가능 — fail-safe 게이트가 막는다** | 프리뷰는 로드 시점 스냅숏이지만 **실행은 `actions.rs:201`에서 `ResolvedRunners::resolve()`를 다시 부른다.** 그 사이 winget이 설치/제거돼 plan이 바뀌면 plan_id가 어긋나 `"실행 계획이 미리보기 이후 바뀌었습니다. 다시 미리보기를 요청해주세요."`로 거부된다(`actions.rs:75-80`, `:207-213`). **방향이 fail-safe다.** 그리고 화면에 낡은 프리뷰가 남는 성질은 brew/npm/pnpm이 **이미 갖고 있던 것**이다 — 이제 네 러너의 신선도 정책이 비로소 일치한다 |

→ **종합: 승격은 N2·M1에 중립이고, 일관성 면에서는 개선이다.** 유일한 실제 변화는 V5(macOS 스폰 프로브 1회).

### Q4. 설계서와 코드의 불일치(이탈 #1 철회)를 어떻게 정리하는가
**V3의 처방 ①②③ 그대로.** 요지는 두 가지다.
1. **철회를 "없던 일"로 만들지 말고 명시적으로 기록한다** — 원래 결정과 철회 사유(그 결정이 불변식 검사 능력을 무력화했다)를 함께. 이탈 승인을 내린 것은 1라운드의 나이므로, **리뷰어의 승인이 틀렸던 사례**로 남기는 것이 다음 라운드에 쓸모 있다.
2. **C.3.1의 증명 수단을 지킬 수 있는 형태로 재정의한다** — "기존 테스트 0개 수정"은 이제 참이 아니고, 참이 아닌 채로 두면 다음 라운드가 그것을 근거로 또 잘못된 이탈을 승인한다. "프로덕션 diff가 macOS 실행경로를 지나지 않음 + 어서션 본문 0개 수정(구조체 리터럴 필드 가산은 허용)"이 대체안이다.

## 5. 페르소나별 관점

### 정직성 감사자(claimed ≠ verified) — 합격선 V1~V4 중 **V4 미충족**
이 커밋의 **정직성은 눈에 띄게 높다.** "logs를 열지 않고 단정했던 이전 보고가 틀렸다"를 커밋 메시지 첫 줄에 적었고, Windows 등가물마다 "미검증 — Windows CI 전용"을 붙였으며, 로컬 테스트 수의 증감(343/15 → 342/17)을 **분해해서** 설명했다. 이건 이 브랜치 전체에서 가장 좋은 보고 품질이다.
그럼에도 V4(주석의 단언 vs 실제 분기)는 **미충족**이다 — 세 건이 걸린다: "#[ignore]가 유일한 수단이다"(V4), "프로세스 스폰 없음"(V5), "캐시 필드가 없어 요청마다 새로 해석"(V6①). 세 건 모두 **사실관계 자체는 성실히 조사한 흔적이 있는데 결론 문장이 한 칸씩 넓다.** 이 브랜치에서 반복되는 패턴이다(r3의 T2도 같은 유형).

### 설계·계약 감사자 — 합격선 D1~D4 중 **D3·D5 미충족**
**D2(불변식을 깨는 변경이 자동으로 잡히는가)는 이번 커밋이 실질적으로 개선했다** — winget 필드 승격 전에는 "러너가 없으면 Manual"이 사람의 주의력에조차 기대지 못하는 상태였다(테스트가 있었는데 그 테스트가 무력했다). 승격으로 타입이 강제하게 됐다.
그러나 **D3(조용한 누락 0건)는 V2로 미충족** — 승격으로 얻은 주입 능력의 양성 방향이 비어 있다. **D5(문서 모순을 구현이 해소했다면 그 선택이 남았는가)는 V3으로 미충족** — 선택은 `runners.rs` 주석에 아주 길게 남았지만, **설계 정본 3곳은 여전히 반대를 말한다.** 코드 주석과 설계서가 갈릴 때 다음 세션이 어느 쪽을 읽을지는 통제할 수 없다.
D4(실패 방향)는 ✅ — staleness가 plan_id 게이트로 fail-safe하게 떨어진다.

### 이기종 머신 운영자 — 합격선 O1~O3 **충족**
O1~O3에 걸리는 것이 없다(이 커밋은 사용자에게 보이는 경로를 바꾸지 않는다). **O5(화면 1회 로드의 스폰 수·최악 대기가 예측 가능한가)만 +1**: macOS 로드당 실패 spawn 1회(V5). 예측 가능하고 상한이 있으므로 권장 기준 위반은 아니되, "무변경"이라는 주장과는 어긋난다.
사내 PC 관점의 가장 중요한 진전은 **Windows kill 경로가 처음으로 실증됐다**는 것이다(Q2). 다만 EDR 환경은 여전히 미검증 — 실기 배포 체크리스트에 "타임아웃 발생 시 자식 프로세스가 실제로 사라지는가"를 **EDR이 도는 실제 사내 PC에서** 확인하는 항목으로 넣어야 한다.

### 제로베이스 재설계자 (발산형) — 🔵 Rethink 1건

**🔵 R-5 — "CI를 초록으로 만든다"를 목표로 두는 한 이번 같은 라운드가 반복된다. 목표를 "각 테스트가 어느 플랫폼에서 무엇을 검증하는지 선언하게 한다"로 바꾼다.**

- **R1(지웠을 때 반드시 남아야 하는 것)**: "이 불변식은 이 플랫폼에서 이 수단으로 검사된다"는 **매핑**. 초록/빨강은 그 매핑의 부산물이다.
- **R2(대안 구조)**: `#[cfg(unix)] / #[cfg(windows)]`를 손으로 흩뿌리는 대신, 테스트 모듈 상단에 **플랫폼 커버리지 표를 하나의 상수로 선언**하고 각 테스트가 그 표의 행을 참조하게 한다. 최소 형태는 헬퍼 매크로 하나다 — `platform_test!(unix: …, windows: …, invariant: "stdin=null이면 읽는 자식이 빨리 죽는다")`. 매크로가 **양쪽 슬롯을 모두 요구**하면, Windows 슬롯을 비우는 순간 컴파일이 멈추고 `todo!("Windows 미구현")`을 명시적으로 적어야 한다. V1(`/bin/cat`)은 이 구조에서 **작성 시점에** 걸린다 — CI 로그에 나타나지 않는 결함이므로 지금 구조로는 영원히 안 걸린다.
- **R3(사용자 목표 기준으로 나은 이유)**: 이 앱의 사용자 목표는 "내 Windows PC에서 도구가 실제로 설치된다"이지 "CI가 초록이다"가 아니다. 현재 구조는 **후자만 보이게 만들어** 3차→4차에서 실제로 오판(PM의 "무관한 기존 테스트" 단정)을 유발했다. 선언형 표는 "Windows에서 검사되지 않는 불변식 목록"을 **항상 조회 가능하게** 만든다 — 실기 배포 전 체크리스트가 그 목록에서 자동으로 나온다.
- **R4(포기하는 것과 그 대가)**: 매크로 한 겹이 추가돼 테스트 코드의 즉시 가독성이 떨어진다(`cargo test` 출력의 테스트 이름도 매크로가 생성하게 되면 grep이 어려워진다). 대가를 감당하는 방법: **매크로는 이름을 생성하지 않고 받기만 한다**(이름은 지금처럼 손으로 적는다) — 그러면 잃는 것은 "선언 한 줄"뿐이다. 그리고 6개 도구·3개 플랫폼 규모에서 표가 과잉일 수 있으므로, **이번 브랜치에는 넣지 않는다** — 실기 검증이 끝난 뒤 Windows 커버리지 공백이 실제로 몇 건인지 세고 나서 판단한다.
- **R5(기존 선례와 정합)**: 정합한다. 이 코드베이스는 이미 `platform_tests.rs`에서 **골든 테스트에 `Platform::Mac`/`Platform::Win`을 둘 다 주입하는 패턴**을 쓰고 있다(`process.rs:485-492` 주석이 그 사실을 인용한다). R-5는 그 패턴을 "순수 함수"에서 "실행 경로 테스트"로 확장하는 것일 뿐이다.

> r3의 R-4(`RunPlan`에 `PreviewCapability` 선언형 필드)는 **유지되며 여전히 이번 브랜치 밖이다.** R-5와 R-4는 같은 병(낙관적 기본값이 판단을 대신한다)의 두 부위다.

## 7. 잘 된 점 (다음 라운드의 기준)

1. **로그를 열어 8건을 개별 처리했고, 이전 단정이 틀렸음을 커밋 메시지 첫 줄에 적었다.** 이 브랜치에서 claimed≠verified 위반이 **자기 교정된 첫 사례**다.
2. **winget 필드 승격은 이번 커밋에서 가장 중요하고, 판단이 옳다.** "테스트 하나가 거짓 실패한다"를 파고들어 **"그 테스트는 애초에 불변식을 검사할 능력이 없었다"**는 더 깊은 결함에 도달했다. 이건 증상이 아니라 원인을 고친 것이고, 1라운드에 내가 승인한 이탈이 틀렸음을 드러냈다.
3. **기대값을 바꾼 유일한 자리에서 "왜 로직이 옳은가"를 먼저 논증했다**(`diagnostics.rs:196-211` 주석). 그리고 원래 검사하지 않던 true 분기를 **함께 추가**해 커버리지를 늘렸다 — 기대값 수정이 은폐가 되지 않는 모범 형태다.
4. **모든 Windows 신규 테스트에 "미검증 — Windows CI 전용"을 명시했다.** 컴파일조차 되지 않는다는 이유까지 적었다.
5. **테스트 코드에도 절대경로 원칙을 적용했다**(`cmd.exe`를 bare-name이 아니라 `C:\Windows\System32\cmd.exe`로). 프로덕션의 하이재킹 방지 원칙을 테스트가 무너뜨리지 않았다.

## 9. 정직 보고 — 이 리뷰가 하지 않은 것

- **Windows 실기 동작은 여전히 미검증이다.** CI 초록은 "테스트가 통과했다"이지 "기능이 올바르다"가 아니다. 이 보고서의 어떤 ✅도 "Windows에서 동작한다"를 뜻하지 않는다.
- **테스트를 직접 돌리지 않았다.** PM이 실증한 수치(CI run 34970379601: windows 334/0/17, macos 342/0/17, 로컬 342/17)를 재측정 없이 그대로 받았다. 내가 한 것은 **코드 읽기와 손 추적**이다.
- **V5의 macOS spawn 프로브는 코드 경로로 확정했을 뿐 실행 계측을 하지 않았다.** "수 ms"는 ENOENT 즉시 실패라는 성질에서 나온 추정이다(경로 자체는 추정이 아니다).
- **워킹트리의 미커밋 변경은 읽지 않았다.** `src-tauri/src/dev_tools/process.rs` 등에 다른 세션의 변경이 있으므로, 이 보고서의 모든 라인 번호는 **`d906867` 시점 기준**이다. 현재 워킹트리와 다를 수 있다.
- **3차에서 종결된 T1~T7·N1~N3·M1~M3는 재검토하지 않았다**(PM 지시). 다만 r3의 머지 선행조건 T2①이 반영됐는지는 상태 확인 목적으로 1회 조회했고, **반영돼 있다**.
- **화면 리뷰 없음** — 이 커밋에 UI 변경이 없다(6파일 전부 `src-tauri/`). 캡처 생략은 스코프 부재이지 미실시가 아니다.
