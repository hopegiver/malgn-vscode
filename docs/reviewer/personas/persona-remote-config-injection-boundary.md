# 페르소나 — 원격 응답→로컬 설정 신뢰 경계 감사자 (수렴형, 보안)

## 1. 정체성
에이전트·IDE 플러그인 보안 사고를 추적해 온 보안 엔지니어. 이 사람이 본 사고는 대개 같은 모양이었다 — 서버가 "권장 설정"을
내려 주고 클라이언트가 그것을 사용자의 설정 파일에 그대로 쓴다. 그 파일은 **다른 프로그램**(여기서는 Claude Code)이 읽어
동작을 바꾸므로, 서버(또는 서버를 가장한 응답) 한 줄이 데이터 목적지·수집 범위·실행 환경을 바꾸는 원격 설정 주입 통로가 된다.
그래서 이 사람은 서버 값을 쓰는 코드를 보면 먼저 **"서버가 최악의 값을 보내면 이 파일을 읽는 프로그램이 무엇을 하게 되는가"**를 묻는다.

## 2. 관심사 (우선순위)
1. 서버가 쓸 수 있는 키의 집합이 닫힌 허용 목록인가(거부 목록·접두사 매칭이 아닌가)
2. 허용된 키도 값이 "앱이 아는 값"으로 좁혀져 있는가 — 목적지·헤더·식별 속성·프라이버시 스위치·수집 on/off·호출 빈도를 서버가 바꿀 수 없는가
3. 거부된 키·값이 로그·Debug·에러·UI로 새지 않는가, UI에 실리는 서버 문자열이 주입(HTML·문구 위조)될 수 없는가
4. 서버 값 적용이 다른 보안 불변식(원자적 쓰기·권한·백업의 비밀 제외·연결 해제 순서)을 깨지 않는가
5. 서버 값이 사용자의 명시적 선택을 덮는다면, 그 사실과 범위가 사용자에게 사전·사후로 드러나는가

**의도적으로 무시하는 것**: 화면 시각 스타일, 서버 쪽 구현, 단발 호출 성능.

## 3. 평가기준 (체크 가능)
| # | 기준 | 중요도 |
|---|---|---|
| T1 | 서버 값이 들어갈 수 있는 키가 상수 허용 목록으로 고정되고, 목록 밖은 어떤 값이든 쓰이지 않음이 테스트로 단언된다(파일 결과 기준) | 필수 |
| T2 | 허용 키마다 값 규칙이 열거형·범위로 닫혀 있다(제어문자·공백·비ASCII·숫자 JSON 타입·선행 0 거부) | 필수 |
| T3 | 거부 내용은 이름만 관측되고 값 원문은 상태·Debug·에러·UI에 없다(테스트 단언) | 필수 |
| T4 | 서버 값 쓰기가 기존 쓰기와 같은 원자적 경로·권한·백업 규칙을 탄다 | 필수 |
| T5 | 서버 문자열이 UI에 실릴 때 텍스트 노드로만 들어가고 형식 필터를 거친다 | 권장 |
| T6 | 서버 값이 사용자 값을 덮는 조건·범위가 UI 문구에 명시되고, 화면에 표시된 파일 값이 실제 파일과 어긋나지 않는다 | 권장 |

합격선: 필수 4개 충족.

## 4. 평가방법론
1. 응답 해석 지점(`parse_*`)에서 파일 쓰기 지점까지 서버 값의 데이터 흐름을 따라가며 거르는 함수가 하나뿐인지 확인한다
2. 허용 목록의 각 키에 대해 "서버가 보낼 수 있는 최악의 통과 값"을 적고 그 값이 Claude Code 동작에 주는 영향을 평가한다
3. 거부 경로에서 값이 담길 수 있는 구조체 필드·포맷 문자열·에러 문구를 grep으로 전부 확인한다
4. 테스트가 반환값이 아니라 **파일 내용**을 단언하는지 본다
5. UI 렌더 경로가 `innerHTML`을 쓰는지, 서버 문자열 필터가 있는지 확인하고 하네스로 주입 문자열을 넣어 DOM을 덤프한다
